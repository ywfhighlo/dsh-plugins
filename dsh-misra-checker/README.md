# @local/dsh-misra-checker

MISRA C checker plugin for DeepSeek Harness — **portable, self-contained folder**.

- Adds a "MISRA C check" panel under the conversation composer: pick (Browse…) or
  enter a project directory and click the button to run a check.
- **Directory *and* file scope**: the panel lists the C sources of the target
  directory, marks auto-generated artifacts, and lets you tick the exact files
  to check (buttons: select all / hand-written only / clear).
- **Generated code is skipped by default** — it usually makes up most of the
  findings in an AUTOSAR/MCAL tree.
- Engine: the bundled `vendor/cppcheck/cppcheck.exe` (v2.22) with the MISRA addon
  runs out of the box; without it the plugin falls back to a built-in heuristic
  scan over a small subset of MISRA C:2012 rules (7.1, 13.4, 15.1, 19.2, 20.10, 21.3).
- Every finding carries the **MISRA C:2012 rule text** (English), the **Chinese
  requirement** and the **Mandatory/Advisory** level.
- Every run writes a **Markdown report** into the project. The panel shows the
  report path as a link: clicking it opens the report in the right-hand document
  preview, and **Send to AI** hands the report summary to the agent so it can
  analyse the findings.
- Also registers the `/misra [path]` slash command, which defaults to the session cwd.
  `/misra report` re-sends the previous run's summary without scanning again.
- The misra addon needs **Python 3** on PATH for some rules to be reported.

## Take it with you

The whole folder is relocatable — cppcheck, the MISRA addon, the rule texts and
all Node dependencies (`node_modules/`) live inside it, and the cppcheck path is
resolved **relative to this folder**, so no config edits are needed after moving it:

1. Copy the `dsh-misra-checker` folder anywhere (any drive, any machine).
2. In DeepSeek Harness: Settings → Plugins → Install bundle → select the folder
   (or ask the agent to run `plugin_manager install_bundle` with its path).
3. Restart/refresh; the panel appears under the composer.

## Default target

The panel prefills the directory with **the current project** — the working
directory of the live session — narrowed by the `subdir` config, so a whole
project tree is never scanned. The `Browse…` button overrides it for one run.

## Scope rules

The report only contains what you asked for:

| selection | analyzed | reported |
| --- | --- | --- |
| a directory | every C/H file in it (minus generated ones) | findings in those files |
| a file list | exactly the ticked files | findings in those files only |

Two details matter in real projects:

- **Included headers are analyzed too.** cppcheck treats a header as part of the
  translation unit, so a violation inside a generated header would still show up.
  The plugin therefore suppresses `misra-c2012-*` for every detected generated
  file and drops findings that live outside the selected scope (for example the
  shared BSW headers in `components/Mcal/Common`).
- **Generated code detection** uses the file-name patterns in `generatedPatterns`
  plus generator markers in the file header (`@implements …_Artifact`,
  `VendorSpecifc File Header`, ARK `<#>` comments, "generated by", …).

## Rule texts

`rules/misra-c2012.json` holds, for every MISRA C:2012 rule, the rule text
(English), the Chinese requirement and the Mandatory/Advisory level. It is
handed to cppcheck through the addon's `--rule-texts` option (see
`vendor/cppcheck/misra-rules.txt`), so the tool reports the rule itself instead
of a placeholder.

The data is generated by `tools/build-rule-texts.mjs` from the public
[MISRA C:2012 中文详解](https://www.cnblogs.com/xywml/p/18742061) summary; the
few rules that page does not list are taken from what cppcheck's own MISRA addon
checks.

## The report file

Each run writes `misra-reports/MISRA-report-<timestamp>.md` into the project root
(configurable through `reportDir`, disabled with `writeReport: false`). It holds
the run metadata, the rule distribution, the file distribution and the full
detail table (line, rule, level, English rule text, Chinese requirement).

The panel shows the report as a link:

- **Open report** opens it in the right-hand document preview (the built-in
  Markdown renderer), through the session's file address.
- **Send to AI** runs the `/misra report` command, so the agent receives the
  summary — including the absolute report path — and can read and analyse the
  file itself. When the command channel is unavailable the summary is copied to
  the clipboard instead.

Only the newest `reportKeep` reports are kept; older ones are removed.

## Intermediate files

The plugin treats the source tree as read-only. Every intermediate file — the
file list, the addon descriptor and the cppcheck cache (`--cppcheck-build-dir`) —
lives in the **system temp directory** and is removed after the run. Set
`tempDir` to place them somewhere else.

The report file is the only thing the plugin writes into the project, and it is
the run's output, not a leftover.

## Config

| key | default | meaning |
| --- | --- | --- |
| `root` | `""` | explicit project root; overrides the session directory |
| `subdir` | `""` | folder below the project root that holds the code (e.g. `components/Mcal/Eth`) |
| `cppcheck` | `"vendor/cppcheck/cppcheck.exe"` | absolute path, path relative to this plugin folder, or a bare command name on PATH |
| `cppcheckArgs` | `""` | extra cppcheck arguments (e.g. `--std=c11`) |
| `enable` | `"warning,style"` | cppcheck `--enable` categories |
| `inlineSuppressions` | `true` | honour inline `cppcheck-suppress` comments |
| `suppressionsFile` | `""` | cppcheck suppressions list, absolute or relative to the project root |
| `maxConfigs` | `1` | `--max-configs`; 1 = default configuration only (fast) |
| `ctuDepth` | `0` | `--max-ctu-depth`; cross-TU analysis, 0 disables it |
| `timeoutMs` | `900000` | cppcheck run timeout |
| `ruleTexts` | `true` | report the MISRA rule text with every finding |
| `tempDir` | `""` | directory for intermediate files; empty = system temp |
| `defines` | `[]` | preprocessor defines for cppcheck (e.g. `DISABLE_MCAL_INTERMODULE_ASR_CHECK`) |
| `includes` | `[]` | include directories, absolute or relative to the project root |
| `exclude` | `.git, node_modules, build, dist, out, .dsh, .agents` | dirs skipped by the built-in scanner |
| `excludeGenerated` | `true` | skip auto-generated files |
| `generatedPatterns` | `*_PBcfg.*, *_regdef.h, *_reg.h` | file-name patterns treated as auto-generated |
| `maxFindings` | `500` | cap on reported findings |
| `writeReport` | `true` | write a Markdown report of every run into the project |
| `reportDir` | `"misra-reports"` | report folder, relative to the project root (empty = project root) |
| `reportKeep` | `20` | how many reports to keep; older ones are removed |

### AUTOSAR / MCAL projects

Generated headers abort preprocessing when the inter-module version check
fails, which makes cppcheck report nothing. Define
`DISABLE_MCAL_INTERMODULE_ASR_CHECK` and add the shared header folder to
`includes` (for example `components/Mcal/Common`, where `Eth_GeneralTypes.h`
lives) — the shipped `cordis.patch.yml` shows this for the Eth module.

The built-in scanner is only a fallback: it approximates a few textually
detectable rules. Real coverage comes from the bundled cppcheck.

### Reusing the project's own baseline

If the project already keeps a cppcheck suppression list (for example
`tools/misra/suppressions.txt`), point `suppressionsFile` at it and the plugin
reports exactly the same baseline as the project's own script — including its
inline `cppcheck-suppress` comments, which need `inlineSuppressions: true`.

### Speed

`--max-configs` and `--max-ctu-depth` dominate the run time. The defaults
(`maxConfigs: 1`, `ctuDepth: 0`) finish a medium MCAL folder in well under a
minute; raising them to `20` / `4` (what `tools/misra/cppcheck-misra.sh` uses)
can take several minutes and finds more cross-TU issues (Rule 8.7 in particular).

## Host API

`POST /api/misra/check` with `{ action, … }`:

| action | payload | result |
| --- | --- | --- |
| `defaults` | – | the default target directory, the session id and where it came from |
| `list` | `{ dir }` | the C sources of a directory with their `generated` flag |
| `check` | `{ dir, files?, excludeGenerated? }` | findings, counts, notes and the written report |
| `summary` | – | the chat summary of the last run (no scan) |
| `diag` | – | paths and versions used by the Host |

A finding looks like
`{ file, line, rule, level, severity, message, zh }`.
